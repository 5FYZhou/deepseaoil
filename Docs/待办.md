- **`UIMgr.HidePanel` 从不 `Pop` `openPanels` ⇒ 栈单调堆积**：`Push` 在 `Presentation/UI/UIMgr.cs:234`（缓存命中直接重显）与 `:289`（协程加载完），`Pop` 只在 `TryCloseTopmostPanel`（`:374` / `:383`）与 `CloseAllPanels`（`:403`）；`HidePanel`（`:292-322`）一条成功路径都不 `Pop`。**现象**：同一面板反复显隐（`SettingPanel` 反复开关最典型）后，该层栈里堆着一串 `isHide == true` 的壳。**后果**：`TryCloseTopmostPanel` 得先逐个 Peek/Pop 空壳才轮到真正在显的面板 —— 表现为按 ESC"关不掉 / 要按好几次"。**修法**：`HidePanel` 的成功隐藏路径补一次该层的 `Pop`（注意与既有 `Pop` 点去重，别在 `TryCloseTopmostPanel` 里二次弹掉）。

## 池与驱动

- **`EffectId.MudSplash` 有 `Preload`、0 个 `Play` 调用点**：`Presentation/Effects/EffectCatalog.cs:79` 登记为 `Particle` / `isSingleton: false` / `prewarm: 4`，`EffectModule.cs:16` 的预加载表也含它，但全仓 `git grep` **0 个 `Play(EffectId.MudSplash` 调用点**。**后果**：白占 4 个池位（每次 `Init` 都预创建），画面上一次都不会出现 —— 想"泥浆溅射"必须先在调用方写一次 `Play`（同节的 `BurstSparks` 就是这么接上的）。**修法**：要么在泥浆相关事件（球落泥 / 泥浆减速跨阶）补 `Play`，要么把 `prewarm` 归 0 以免虚占。

## 生命周期

- **`Singleton<T>` 无 `OnDestroy` 清 `instance`，而 getter 会"无中生有"造对象**：`Foundation/Singleton.cs:7-24` 的 getter 在 `instance == null` 时先 `FindObjectOfType`、落空就 `new GameObject(...) + AddComponent + DontDestroyOnLoad`；全类**没有 `OnDestroy`** 把 `instance` 置空。**后果**：销毁期再问 `.Instance` 会**当场造一个新的常驻对象**（旧引用全失效、状态归零）。**现状**：全仓只有 `GameRoot` 继承它（`Presentation/Root/GameRoot.cs:20`），曾被点名的 4 个隐患点都已改成"`Start` 缓存引用"并留了注释自证 —— `Presentation/Input/InputProvider.cs:83`/`:90`、`Presentation/Root/SceneFlowConfig.cs:31`/`:37`、`Presentation/Root/CombatRoot.cs:88`/`:104`、`Presentation/Root/PlayerController.cs:203`/`:209`。**修法**：补 `OnDestroy` 里 `if (ReferenceEquals(instance, this)) instance = null;` —— 但**改之前必须**跑完整 `Begin → CG → Game → 返回菜单 → 再进 Game → Quit` 回归（getter 的"自动重建"正是现在掩盖某些缺失引用的东西，补上才会把问题暴露出来）。
- **`CombatRoot.OnDestroy` 只 `Detach` 表现件，三张表不清**：`Presentation/Root/CombatRoot.cs:99-106` 只做 `_highlight?.Detach()` / `gridView?.Detach()` 与 `_root.UnregisterSceneRoot(this)`，`_balls`（`:60`）/ `_drops`（`:64`）/ `_combat`（`:66`）都没有 `ClearAll`。**后果**：**当前不泄漏**（三者随 `CombatRoot` 一起被场景卸载），属**防御与对称性** —— 哪天改成"根常驻、场景换"，上一局的球 / 掉落物 / 波次状态就会被带进下一局。**修法**：`OnDestroy` 里补一次 `ClearAll()`（`:311-330` 已覆盖 `_combat` / `_balls` / `_drops` / `gridView`）；注意它会连带 `TileChainReactor.Clear()`（`:320`）与销毁波次怪（`:325-`），销毁期调用要先确认没有反序依赖。

## 明示约定（先讨论，不要顺手改）

- **`AssetModule.Load` 不配对 `Release` 是明示的工程约定，代价是 `LifecycleMgr` 永远淘汰不掉这两个键**：`Presentation/Adapters/TilemapAdapter.cs:546`（`Load<TileBase>("tiles/Tile_<state>")`，结果进 `_runtimeTileCache`：`:70` 声明 / `:540` 查 / `:555` 写）与 `Presentation/UI/Panel/HudPanel.cs:147`（`Load<Sprite>(spec.IconKey)`，`:146` 的注释自认"与 TilemapAdapter 同口径"）都**不配对 `AssetModule.Release`**。**后果**：这两个键的 refCount **永久 > 0** ⇒ `LifecycleMgr` 的 LRU 淘汰对它们永不生效（等于常驻，这正是想要的效果）；`HudPanel` 更狠 —— 每次 `PlayerAmmoChanged`（`:94` 订阅 → `:118` → `:125` → `UpdateSeedIcon` → `:147`）都再 `Load` 一次，refCount 只涨不落。**修法**：**先讨论**"refCount 到底该不该表达常驻" —— 直接补 `Release` 会把地块 / 种子图标变成可淘汰（切场景重新加载、可能掉帧）；要真收口得先给 `AssetModule` 一个显式的"钉住 / 常驻"口径（如 pin 到进程结束），再谈 LRU 行为怎么改。
- **`GameRoot` 用延期 `Destroy` 拆 UI，面板的 `ReleaseAssets` 实际跑在 `AssetModule.Dispose` 之后**：`Presentation/Root/GameRoot.cs:311` 调 `UI?.Dispose()`，而 `UIMgr.Dispose`（`Presentation/UI/UIMgr.cs:125-155`）用 `GameObject.Destroy`（`:145-147`）把 `EventSystem` / `Canvas` / `Camera` **延到帧末**销毁；`AssetModule.Dispose` 在同方法 `GameRoot.cs:322` **同步**跑完。**后果**：帧末 `BasePanel.OnDestroy`（`Presentation/UI/BasePanel.cs:36-39`）→ `ReleaseAssets`（`:186`）时 `AssetModule` 已经关灯（引用归还被静默吞掉）—— **后果为零**（进程要退了），但 `GameRoot.cs:300` 那句"`AssetModule.Dispose` 必须最后"的理由**对 `UIMgr` 不成立**，别照它推结论。**修法**：把注释改成"只保证 `EffectModule` / `UIMgr` 的**显式** `Release` 先于 `AssetModule.Dispose`；面板自身的 `ReleaseAssets` 走延期销毁、必然在其后"。
