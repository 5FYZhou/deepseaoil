## 🔴 已确认的缺陷 / 对称性缺口（只报不改，各带最小修法）

> 分组按主题；每条按「现象 → 后果 → 最小修法」写。多数**当前不可达**或后果为零，属防御性补丁。

### UI 栈与加载

- **`UIMgr.HidePanel` 从不 `Pop` `openPanels` ⇒ 栈单调堆积**：`Push` 在缓存命中与协程加载完两处，
  `Pop` 只在 `TryCloseTopmostPanel` 与 `CloseAllPanels`；`HidePanel` 一条成功路径都不 `Pop`。
  **现象**：同一面板反复显隐（`SettingPanel` 反复开关最典型）后，该层栈里堆着一串 `isHide == true` 的壳。
  **后果**：`TryCloseTopmostPanel` 得先逐个 Peek/Pop 空壳才轮到真正在显的面板 —— 表现为按 ESC"关不掉 / 要按好几次"。
  **修法**：`HidePanel` 的成功隐藏路径补一次该层的 `Pop`（注意与既有 `Pop` 点去重）。
- **`UIMgr.CoLoadPanel` 的降级分支缺 `Release(key)`**：「`prefab == null` ⇒ 摘掉 `panelDic` 占位」这条
  `yield break` 前**没有** `AssetModule.Release(key)`（另两条退出分支都有）。
  **后果**：refCount 永久 +1，`LifecycleMgr` 再也淘汰不了该键。
  **当前无可达路径**：只有"缓存命中且资源已被销毁"才会进这个分支，而 refCount > 0 的键不会被淘汰 ⇒ 属**对称性补丁**。
- **`GameRoot` 用延期 `Destroy` 拆 UI，面板的 `ReleaseAssets` 实际跑在 `AssetModule.Dispose` 之后**：
  `UIMgr.Dispose` 用 `GameObject.Destroy` 把 `EventSystem` / `Canvas` / `Camera` **延到帧末**销毁；
  `AssetModule.Dispose` 在 `GameRoot` 拆除流程里**同步**跑完。**后果**：帧末 `BasePanel.OnDestroy` →
  `ReleaseAssets` 时 `AssetModule` 已经关灯（引用归还被静默吞掉）—— **后果为零**（进程要退了），
  但 `GameRoot` 里那句"`AssetModule.Dispose` 必须最后"的理由**对 `UIMgr` 不成立**，别照它推结论。
  **修法**：把注释改成"只保证 `EffectModule` / `UIMgr` 的**显式** `Release` 先于 `AssetModule.Dispose`；
  面板自身的 `ReleaseAssets` 走延期销毁、必然在其后"。

### 池与驱动

- **音频两个池无上限、只增不减，且在热路径 `LogWarning`**：`AudioManager` 的 `_audioPool` 与 `_entryPool`
  都用 `PoolInClass`，而它（`Foundation/Pool.cs`）签名里根本没有 `maxSize`，落到底座默认
  `maxSize = int.MaxValue` + `PoolOverflowPolicy.CreateAndWarn`。
  **后果**：① 池容量等于历史峰值，音频对象只增不减；② 池瞬时见底时走 `Pool.cs` 的
  `Debug.LogWarning(...池为空，正在现场创建对象...)` —— 这条警告出在**播放热路径**上。
  **修法**：给 `PoolInClass` 透传 `maxSize` / 溢出策略，音频按同时发声上限定容，并把溢出策略从
  `CreateAndWarn` 改成静默复用最旧条目。
- **`TileOverlayDirector.ClearAll` 缺 `_pool == null` 守卫**：`ClearAll` 直接 `_pool.Release(kv.Value)`；
  兄弟件 `Presentation/Grid/TileObstacleDirector.cs` 的同名方法第一行就是 `if (_pool == null) return;`。
  **后果**：`OnDestroy` 先 `Detach` 再 `_pool?.Dispose()` 并把 `_pool` 置 null，若此后有别的路径调 `ClearAll`
  就 NRE；**当前被 `_attached` 挡住**，属**潜在 NRE**。**修法**：照抄兄弟件那行守卫。

### 生命周期

- **`Singleton<T>` 无 `OnDestroy` 清 `instance`，而 getter 会"无中生有"造对象**：getter 在 `instance == null`
  时先 `FindObjectOfType`、落空就 `new GameObject(...) + AddComponent + DontDestroyOnLoad`；全类**没有 `OnDestroy`**。
  **后果**：销毁期再问 `.Instance` 会**当场造一个新的常驻对象**（旧引用全失效、状态归零）。
  **现状**：全仓只有 `GameRoot` 继承它，曾被点名的 4 个隐患点都已改成"`Start` 缓存引用"并留了注释自证。
  **修法**：补 `OnDestroy` 里 `if (ReferenceEquals(instance, this)) instance = null;` —— 但**改之前必须**跑完整
  `Begin → CG → Game → 返回菜单 → 再进 Game → Quit` 回归（getter 的"自动重建"正是现在掩盖某些缺失引用的东西）。
- **`CombatRoot.OnDestroy` 只 `Detach` 表现件，三张表不清**：只做 `_highlight?.Detach()` / `gridView?.Detach()` 与
  `_root.UnregisterSceneRoot(this)`，`_balls` / `_drops` / `_combat` 都没有 `ClearAll`。
  **后果**：**当前不泄漏**（三者随 `CombatRoot` 一起被场景卸载），属**防御与对称性** —— 哪天改成"根常驻、场景换"，
  上一局的球 / 掉落物 / 波次状态就会被带进下一局。**修法**：`OnDestroy` 里补一次 `ClearAll()`；
  注意它会连带 `TileChainReactor.Clear()` 与销毁波次怪，销毁期调用要先确认没有反序依赖。

### 未收口

- **`ActorLedger.SteerTowards` 的反向分支（点积 < 0）不做加速度限幅**：那一支取「指数衰减」与「`desired − current`」中**较快**的一支，
  而夹角 > 90° 时 `|desired − current| > |current| > λ|current|` 恒成立（λ = 1−e^(−30Δt) ≈ 0.45）⇒ 实际执行的是**未限幅的整块翻面**，
  配置的 `moveAcceleration` 在这一帧完全不存在。**后果**：任何"期望速度与当前速度夹角 > 90°"的一帧都能把速度整块翻过去；
  离线夹具（`寻路Tests.玩家折返与贴脸顶住都不该抖` 的基线版）实测单帧 |Δv| **5.02 u/s = 251 u/s²**，配置加速度 5 的 **50 倍**。

  **仍未收口**：玩家（击退反向）与将来任何直接 `MoveTowards` 的写法都还暴露在这条上。
  **修法**：反向那一支也用 `acceleration × Δt` 限幅，或在 `MotionParams` 里给一条独立的反向加速度（会改玩家掉头手感，需实机判定）。

## 导电麻痹与种子掉落（核对结论，2026-10）

- **1.5s 连锁麻痹曾是"只记时长、不停人"**：`EnemyActor.ApplyStun` 只写 `_stunnedUntil`，而 `IsStunned`
  **全仓 0 读取点** ⇒ `TileChainReactor` 泛洪算出的 1.5s 麻痹对移动毫无影响，敌人照常满速追击。
  修法：麻痹改由 `StatusGroup` 承接成移动门禁（`MoveGates.Forced(Vector2.zero)`，优先级**高于**硬直推力，
  且麻痹期间退出硬直并丢弃推力 —— 否则解除当帧会把存下的击退补放成滑步）；`EnemyActor.ApplyStun` 只做转发。
  **别再往表现层加麻痹计时字段**：写速度的只有移动层，表现层记时长必然退化成死字段。
- **测试替身曾经"只记不转发"**：`地块效果Tests.GridTarget` 原先把 `ApplyStun` 只记进计数器、不喂给真
  `StatusGroup`，于是"麻痹到底有没有挡住移动"在 EditMode 里**不可见** —— 缺陷能藏住正是因为这个盲区。
  现已转发并补上门禁断言（含 1.5s 到期解禁）。
- **导体的 `touch_stun` 全为 0**：`基础水/基础土/普通泥浆/稀泥/导电区` 五行皆 0，唯一非 0 的
  `带电荆棘 = 1.5` 又**不是导体** ⇒ 导电连锁读表值等于不麻痹。已把 1.5 提为
  `TileChainReactor.ChainStunSeconds` 常量（白皮书 §6.4），不再读 `TouchStunOf`；**行为等价**
  （改前 `Mathf.Max(表值, 1.5f)` 对所有可达导体恒等 1.5）。将来给导体配 `touch_stun > 1.5` 也不会再
  悄悄改变连锁时长 —— 那属于 `element_rule` / 连锁语义，不该由 `tile_state` 决定。
- **带电荆棘的 `touch_stun` 目前只麻痹敌人**：`ApplyStunCell` 只认 `IStunnable`，而全仓仅 `EnemyActor`
  实现它，玩家不是 `IStunnable` ⇒ 玩家踩 `带电荆棘` 不定身。要生效就让 `PlayerActor` 实现 `IStunnable`
  并把麻痹接进 `PlayerLogic.Status`（门禁已就绪，接一根线即可）。
- **`enemy_drop.probability` 只读第 0 行**：`CombatRoot.TryRollDrop` 拿 `rules[0].Probability` 当整张表的
  掉落几率，逐行 `weight` 才参与轮盘赌（`Rng.Range(0, totalWeight)` + 累加扣减，实现正确）。现状 4 行
  probability 全是 1 所以看不出问题；**将来要让不同种子有不同掉率时这个字段不会生效** —— 要么改成逐行判定，
  要么在表里明确"每行同值"。局部实现是干净的：只在 `DefaultRng` 构造器里 `new System.Random`，
  不存在"掉落方法里 `new Random()`"。
- **全局随机流原本是"每次启动完全一样的一份剧本"（已修）**：`DefaultRng` 的默认种子是硬编码常量
  `DefaultSeed = 20261004`，而 `Rng.Reset` / `SetImpl` 在 `Assets/Scripts/**` 里**0 调用点** ⇒ 进程每次都从
  同一个流状态起步。更要命的是 `Rng` 的消费者**全是事件驱动**（`CombatDirector` 每次生成抽 2 次、
  `CombatRoot` 每次掉落抽 4 次、`Fountain` 每次落点抽 2 次），**没有任何一个随帧推进** ⇒ 流的位置只由
  "发生了哪些游戏事件"决定，两局开局走同样的生成/击杀序就拿到同样的掉落。
  实测（`System.Random` 同种子可复现）：旧种子下**前四次精英掉落恒为 `2 2 2 2`（冰）**，每次启动都一样 ——
  这正是"随机度不够"的观感来源。修法：`GameRoot.Assemble` 开头按 `DateTime.UtcNow.Ticks` 重播种
  （`Rng.Reset`）；Presentation → Foundation 是合法方向，且 `Foundation/**` 按纪律**零改动**。
  **代价**：默认不再逐局可复现，要复现请显式 `Rng.Reset(<seed>)`（API 保留）。
  ⚠️ `Foundation/Rng.cs:38` 那句 `固定默认种子，每局一致便于复现` 现在与 `GameRoot` 的重播种**互相矛盾**，
  属 `Foundation/**` 保护区故未改 —— 需要一句注释更正请单独授权。
- **随机度复核数据**：按 `TryRollDrop` 的真实抽数序（`Value01` → `Range(0, 100)` → `InsideUnitCircle` 两次）
  抽样 4000 次，四类占比 26.12 / 23.85 / 24.30 / 25.72 % ⇒ 轮盘赌与随机源**本身没有偏置**，
  唯一的缺陷就是种子固定。**连出同一种是独立均匀抽样的正常现象**（长度 4 的连出概率每 64 次约 1 次），
  不该为"消连出"加保底/去重逻辑 —— 那会引入真正的分布偏置。
- **`PopupDriver._jitterRng` 是另一条独立固定种子流**（`new DefaultRng()`）：只驱动飘字抖动，且**故意与游戏流
  隔离**（观感抖动不该扰动玩法随机），所以它保持固定种子无害，也不该并进全局流。

## 自动存档与即时存档（已落地，2026-10）
