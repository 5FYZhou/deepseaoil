## 7 · 关卡 3 定案：新玩法链路与效果模型（用户决策，2026-10-07）

### 前提更正

**旧链路作废，新链路是最新的**（与策划讨论定，属玩法链路内容）：

```
新链路（五段）
① 球带元素落地
② 球元素 ⊕ 地块元素（ElementCombiner）
③ 合成元素 → 查 element_rule → 新状态 ＋ 效果清单（效果号 + 档位）
④ 切状态 → 提交该状态的进格效果清单
⑤ 逐个效果 → Resolver.Apply(cell, in TileEffect)   ← 出口签名不变
```

**判据（用户原话）**：不要求改动最小化；旧链路本身就是旧设计；只要往宏观设计思想对齐。

### 用户拍板的三条

| # | 决策 | 内容 |
| :-- | :-- | :-- |
| 1 | **地块元素挂在格子上** | `Dictionary<Vector3Int, ElementValue>`（选项 A）。元素是"格子的一块属性"，不是状态的一部分 → **状态机仍可零常驻**，`duration = -1` 的永久地块不必持有状态机 |
| 2 | **旧字段直接删** | `TileStateSpec.EnterDamage` / `EnterKnockback` 删；`OnBallHit(cell, TileStateType next)` 签名换掉。**不留兼容层**——两条链路并存将来分不清哪条是活的 |
| 3 | 效果模型按新链路扩 | 见下 |

### 效果模型（据上述落成的形状）

**核心决议：档位在数据层解决，Logic 层不认识"级别"。**

```
数据层  TileEffectSpec.GetLevel(pos) → TileEffect     ← 多档在这里选好，越界在这里报
Logic   Apply(cell, in TileEffect)                   ← 只看到已定值
```

**理由**："档位"是配置概念，不是行为概念。让它留在数据层，则 `ITileResolver.Apply` 的签名永远不随效果数量增长（这是判断扩法对错的唯一标尺）。

```csharp
// TileEffectKind 扩成 8 个成员（None 保留）
public readonly struct TileEffect {
    public readonly TileEffectKind Kind;
    private readonly float _a, _b, _c;      // 按 Kind 解释；工厂方法保证不会对不上
    public static TileEffect Slow(float scale, float seconds);
    public static TileEffect InstantDamage(float amount, float knockback);
    public static TileEffect Slide(int cells, float seconds);
    public static TileEffect Numbness(float seconds);
    public static TileEffect DamageOverTime(float perTick, float interval, float seconds);
    public static TileEffect InheritElement(float tempRatio, float wetRatio, float condRatio);
    public static TileEffect ClearPlants(int radius);
}

// ApplyEnterImpact 的替代：状态持有"预解析好的效果清单"
var plan = spec.EnterEffects;
for (int i = 0; i < plan.Count; i++) Resolver.Apply(cell, plan[i].ToEffect());
```

**`ToEffect()` 不带参数**：清单在数据层预解析一次，帧内零查表。

### 数据层随之要做的四件事

```
① ProjectileSpec 暴露 Element（球元素）        —— 上游是 BallSpec.Element
② TileStateSpec  暴露 Element（地形元素）      —— 上游是 TileStateSpec.Element
③ 新增 ElementRuleSpec：优先级 + 匹配条件 + 结果状态 + 效果清单
④ 新增 TileEffectSpec：效果号 → 多档参数（value1/value2/interval/flag）
   ＋ 出口：ConfigModule.GetElementRules() / GetTileEffects()
```

### 上游的坑（搬运时注意）

- `ElementCombiner.TryCombiner` 里合成结果的 `Type` **硬编码 `ElementType.Earth`**，是占位写法不是算法。且 `ElementType` 只有 `Water / Earth / Seed / Environment` 四个值，**没有火/冰** → 真正的数据是温度/湿度/导电，`Type` 目前不参与判定。要么明确"Type 不参与判定"，要么先问策划意图。
- 上游 `ITileEffect` / `TileEffectExecutor` / `Register()` 注册表按关卡 1 的 C **不照搬**。

## 9 · 关卡 5 定案：目标接口合并（用户决策，2026-10-07）

**决策：选项 A —— 建 `IEffectTarget`，`IDamageable` 继承它。**

### 接口链（定案形状）

```csharp
public interface IAlivable        { bool IsAlive { get; } }                       // 生死体征，只此一条
public interface IEffectTarget : IAlivable { Vector2 Position { get; } }          // 格子效果的下发目标
public interface IDamageable : IEffectTarget { void TakeDamage(in Damage damage); } // 能受伤
```

- `Position` 从 `IDamageable` **剥离**，"格子效果目标"有了自己的抽象（比上游的 `IEffectTarget.IsDead` 更准确）。
- `IAlivable` 保住"只有一条属性"的纯粹性。
- 上游的 `IEffectTarget.IsDead` 命名**不采用**（与 v2 统一生死体征的裁定冲突，`IsDead` 作为结算窗口的语义不引进）。

### 连带效果（定案即生效）

```
EnemyActor    实现 4 个接口 → 3 个（IDamageable / ISlowable / IManagedActor）
              —— IDamageable : IEffectTarget : IAlivable，不必再单列
PlayerStats   不变，仍只实现 IAlivable（玩家不进归属表，正确）
Registry      泛型 IDamageable → IEffectTarget
GridLogic     _dealScratch 的 List<IDamageable> → List<IEffectTarget>；结算时判 is IDamageable
```

### 用户拍板的两条附带规则

**规则一：留 `ISlowable`，命名风格统一。**
- 本侧 `ISlowEffectTarget` → 并入 `ISlowable`；上游新增的 `IKnockBackable` 同风格，保留。
- 由此确立一条**通用命名规则**：能力接口一律 `-able` 后缀（`IAlivable` / `IEffectTarget` / `IDamageable` / `ISlowable` / `IKnockBackable` / `IManagedActor`）。

**规则二（最高规则级）：`Position` 一律 = 脚底中心。**
- 用户原话：**"这是游戏默认逻辑，出现任何身体中心的描述都应该自己主动显式命名强调"**。
- 即：任何"取位置"的成员，默认语义是脚底中心；需要身体中心（受击点、绕身体旋转、命中判定中心…）的地方**必须自己显式命名**（如 `BodyCenter` / `HitCenter`），不得复用 `Position` 这个名字含糊过去。

### 待决子问题 —— 已收尾（玩家拍板，2026-10-07）

**`ISlowable` 方法形状：选 A。** 保持本侧现状 **`ApplySlow(float scale, float seconds)`**（"续一次修饰"，时长由目标自己管）。
- 不采用上游帧式 `SetSlowMultiplier` ＋ `ResetSlow`。
- 理由：现状是有意设计——离开格子不再续命即自动过期；暂停时格子不 Tick、恢复后立刻续上。换帧式会把"何时复位"的责任拆进格子，多一处状态。

## 11 · 关卡 7 定案：计时器入服务表（用户决策，2026-10-07）

**决策：选项 A —— `IService.Tick` 扩展为收两个 delta 值。**

### 三处接不上 → 三处怎么改

```
① 骨架   TimerManager : BaseManager<TimerManager>  → 脱掉单例，实现 IService
② 双钟   IService.Tick(unscaledDeltaTime)
        → IService.Tick(float deltaTime, float unscaledDeltaTime)
        口径：一律由驱动方给，服务永不自己读 Time
③ 初始化 Init(slotDuration, slotCount) 带参 ≠ IService.Init() 无参
        → 改构造传入：new TimerManager(0.1f, 512)，IService.Init() 保持无参干净
```

### 计时器本身（上游资产，直接收下）

```
TimerWheel      纯 C#、不依赖 Unity（可 EditMode 直测）
TimerHandle     readonly struct，只带 Id
TimerOptions    Once(delay) / Loop(interval)
TimerInfo       Duration / Elapsed / Remaining / Progress / IsRepeating（UI 读条用）

TimerManager 四个入口
  Schedule(delay, cb) / ScheduleUnscaled(delay, cb)                  （一次）
  ScheduleRepeating(interval, cb) / ScheduleRepeatingUnscaled(...)   （循环）
  Cancel(handle) · TryGetInfo(handle, out info) · Clear()
```

### 机制要点（搬之前知道这几条，免得误判它是黑盒）

- 轮子 = **512 槽 × 0.1s = 51.2s 一圈**；每 timer 记 `TargetSlot` ＋ `RemainingRounds`。
- **双层判**：槽号是"粗定位"，`ExpireTime` 是"精确判据" → 精度是绝对时间，分桶只省性能。
- 一次 `Tick` 跨多槽时 **while 逐槽**处理（掉帧不丢）。
- 已处理的坑：① 回调内可建新 timer（进槽先 `ToArray()` ＋ `Clear()`）；② 单帧跨多个循环周期**不补执行**，直接把下次执行推到当前之后；③ 回调内取消自己安全（二次检查 `Cancelled`）；④ 单帧 dt 上限 0.1s。

### 已知边界（不是错，是留个底）

- **`Handle` 只有 Id，两轮共用 id 空间**：`Cancel` 依次问两个轮，"两轮恰好撞同一个 id"时会漏取消一个。**当前规模碰不到，登记备查。**
- id 不回收，到 `int.MaxValue` 回绕到 1 → 长时间运行有极低概率复用。
- **`GridLogic` 及其 `TileTickQueue` 里的 `Schedule` 与计时器无关**（那是格子 tick 队列），别混。

### 用法边界（本轮要遵守）

- 麻痹 1.5 秒、波次间隔、重生倒计时、UI 提示 → **可以用它**。
- **格子上的 DoT 不要用它**：格子本身每帧在 Tick，自己累加时间即可；给每个中毒格挂全局 timer 会让格子数变成 timer 数。

### 上游现状

计时器在 `main` 上**零生产消费者**——只有 `Assets/Tests/TestTimer.cs` 四个入口各打一条 log；`GameRoot` 里只有三行（拿单例 / `Init()` / 每帧 `Tick`）。**能力已备，尚未被接进任何玩法。**

## 13 · 逻辑设计分叉（用户决策，2026-10-07）

> **提问口径（用户立规）**：后续只问**"要不要动框架"**；玩法实现细节放到执行时自行解决，不再逐条确认。

### D7 · 玩家与格子系统：**A 暂时隔离**

维持"玩家不被格子作用"的现状（泥浆不减速玩家、玩家不进归属表）。
**理由（用户原话）**："暂时隔离，避免策划那边突然改口导致要删东西，**加东西比删东西容易**"。
→ 连带：`IEffectTarget` 体系暂不覆盖玩家；`EnemyCellRegistry` 可保持现名；`IStunnable` 暂不给玩家实现。

### D8 · `GridLogic` 职责边界：**B 拆出元素层** ★ 唯一"动框架"的决策

**理由（用户原话）**："不要让 Logic 腐化，应该专职专项"。

```
元素层（新）= 元素合成（ElementCombiner）＋ 规则匹配（ReactionResolver）＋ 元素状态持有
GridLogic   = 格子状态 ＋ Tick 调度 ＋ 效果执行（不再承担反应判定）
接线：元素层由组合根装配，结果（新状态 ＋ 效果清单）交回 GridLogic —— 仍是构造注入，不引入新的全局单例
```

### D9 · 元素与地形状态的关系：**A 要 `tile_state` 的元素列**

地形状态表带 `temp / wet / cond / tags` 四列 → **切进某状态时把该状态的元素刷到格子上**（作初值）。
**理由（用户原话）**："上游是设计好表的，我的玩法设计全都是临时占位性质的，我之前的工作都只是设计框架和宏观依赖关系"。
→ 连带：`TileStateSpec` 要暴露元素四件。

### D10 · 反应效果与地块效果：**A 一个出口**，靠 `Kind` 区分（现状 + 扩展）

### D11 · 效果能不能改地块自身：**A 给出口加通道**

`ITileResolver` 增加 `ApplyToCell(...)` 一类的地形改写通道（供 温湿度继承 / 清除植物 / 状态转换 使用）。

### D12 · 状态效果的时钟：**A 计时器统一托管**（范围经二次决策收窄）

**首轮决策**：麻痹 1.5 秒等"持续到某时刻"的解除，由计时器排程，不由目标自己倒计时。
**理由（用户原话）**："计时的东西尽量走计时器（时间轮），统一管理有性能保证，也更好做'时间效果'"。
→ 连带：`ActorLogic` / 状态机要能拿到计时器（或一个窄接口）——**属框架级接线**。

**二次决策（2026-10-07，收窄范围）：选 A —— 只有 Actor 侧用计时器。**

```
Actor 侧（麻痹/滑行解除）  走计时器        ← 落实"计时统一托管"
格子侧（DoT"每秒掉 0.5"） 状态机每帧自己累加，不由 GridLogic 排计时器
```

**判据**：`GridLogic` 的立身之本是"谁都不认识"（不吃 `ConfigModule`、不吃 `Time`）；注入计时器等于在这个立身之本上开口子。且格子本身每帧就在 Tick，天然有钟——**给已经有钟的地方硬塞一个全局钟，只会让格子数变成 timer 数**（此边界已记在 §11 用法边界）。"计时统一"落实在需要独立钟的地方（麻痹、冷却、倒计时），不硬塞给已有钟的地方。

### D13 · 字段语义：**先保持，不动**

`canReact` / `willSpread` / 球的 `ElementType` 暂时保持上游原样（用户："还不知道未来如何，那就不动它"）。
**已澄清的事实**：上游火池靠 `temp = 4` 表达、不是靠 `ElementType`；`ElementType` 当前不参与判定，枚举里也没有火/冰。
