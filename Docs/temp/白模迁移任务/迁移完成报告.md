## 2. 与设计案的修订（13 处）

> 设计案标注"可信度中、非完全贴合当前项目"。以下是**考据后没有照抄**的地方，逐条给"设计案怎么写 / 实际怎么做 / 为什么"。

### R1 `TileStateMachine` 不共享状态原型

- **设计案**（阶段 3 §1.2）：`Register(ITileState state)` 注册一个**实例**，`_states[id]` 复用。
- **实际**：`Register(TileStateType id, Func<ITileState> factory)`，`SwitchTo` 每次调工厂造**新实例**。
- **为什么**：状态把"已经持续了多久"放在自己字段里（`MudTileState._elapsed`）。共享一份原型 = 全场格子共用一个计时器，现象是"两片泥浆一起消失"，不报错、极难倒推。这是参考骨架里的**真缺陷**。

### R2 端口从三个收敛到一个

- **设计案**（阶段 3 §1.1/§1.2）：`IDamageable` ＋ `IEnemyResolver`（`EnemyId → IDamageable`）＋ `IEnemyCellRegistry`（按 `EnemyId` 记账）。
- **实际**：只保留 `IDamageable`（并给它加了 `Position`，用来算击退方向）；`EnemyCellRegistry` 直接以 `IDamageable` 引用为键，未建 `EnemyId` / `IEnemyResolver`。
- **为什么**：结算方只需要"这一格上站着谁"。多一层编号→目标的解析，每次结算多一次查表，且"谁负责注销"从一处变两处；而 `IDamageable` 本来就是逻辑层唯一的目标准抽象。省掉 2 个文件、1 个字典。

### R3 不建联动空接口

- **设计案**（阶段 3 §1.2）：`ILinkageDispatcher` ＋ `LinkageContext` ＋ 联动计数（接收方递减）。
- **实际**：**没有**这两个类型。保留了两件等价能力：`ITileScheduler.Transition(cell, next)`（一格影响另一格状态的通用通道，本帧 Tick 循环之后统一结算，天然有界）与 `GridQuery` 的三个空间查询。
- **为什么**：本次没有任何联动规则消费者（需求里"复杂联动不做"）。按 KISS，不建只有签名没有实现的抽象；而"状态影响状态"这条路径已经通过 `Transition` 打通，将来加规则不用改框架。设计案自身的"需要/不需要"清单在第 6 条与"复杂联动不做"之间是矛盾的，此处取后者。

### R4 不抽 `RigidbodyMotorBase`

- **设计案**（阶段 2 §2.3/§2.5）：把 `MovementMotor` 的实现上移成 `RigidbodyMotorBase`，`PlayerMotor` / `EnemyMotor` 做空子类。
- **实际**：只新增 `EnemyMotor`（照 `MovementMotor` 的写法独立实现 91 行），`MovementMotor` **一个字没动**。
- **为什么**：`MovementMotor` 是 `sealed` 且被场景资产引用着，抽基类要先改一个正在工作的文件 + 重接线；而两个实现的公共部分只有"取刚体、关重力、冻旋转"。**触发条件**（已写进 `EnemyMotor` 注释）：出现第三个执行器，或敌人侧开始需要"贴墙 / 站地"这类探测时再抽。

### R5 落地双环改为"冲量圈 ＋ 格子圈"，并去掉 0.05 s 错开

- **设计案**（阶段 2 §2.11 / 阶段 1 §3.1）：内圈＝击退半径、外圈＝泥浆半径（水球 1.8 / 土球 1.2），外圈晚 0.05 s 出现。
- **实际**：两个环都叫 `EffectId.LandingRing`，分两次 `Play`：**冲量圈**（半径 `tuning.impulseRadius`、球种色）与**格子圈**（半径 = 半格边长、灰白），**同帧出现**；只有"这一球真的改变了该格状态"时才画格子圈。
- **为什么**：格子系统里泥浆是**整格**而不是一个半径，"泥浆半径 1.8"没有对应物；能精确对应的两件事是"推了多远"与"哪一格变了"。错开的理由（避免两环糊成一个粗环）在"半径差 2.4 倍 ＋ 颜色不同"之后不再必要；不画格子圈则是在撒谎（状态没变）。

### R6 特效分派靠 `DriverKind`，不是"工厂里的 switch"

- **设计案**（阶段 2 §2.9 / 粒子文档 §7）："在 `EffectDriverFactory.Create` 的 `switch` 加一行"。
- **实际**：`EffectSpec` 新增 `EffectDriverKind` 字段，`EffectDriverFactory` 按 `spec.DriverKind` 分派（`Particle` / `LandingRing` / `EnemyShatter`）。**原本那个 `switch` 并不存在** —— 原来的 `Create` 是无条件 `new ParticleDriver(spec, root)`。
- **为什么**：按种类分派允许"多种特效共用一个驱动、只是参数不同"（常见形态）；按 `Id` 分派会让每加一种特效都要动工厂。

### R7 `EffectContext` 扩了三个字段

- **设计案**：`EffectContext` 保持原样（位置 / 方向 / 缩放 / 强度 / 跟随）。
- **实际**：＋`Tint`（alpha 为 0 读取为白）、`Radius`（≤ 0 读取为 1）、`Duration`（不归一化，≤ 0 表示用驱动默认值）。
- **为什么**：落地环的**半径就是它的语义**（"画出来的每个半径都精确等于一件事的生效范围"），颜色区分球种与格子，时长是观感调参 —— 三者都无法从原有字段推出来。拉伸它们的语义（例如拿 `Scale` 当半径比）会立刻产生"没人看得懂"的调用点。粒子驱动忽略这三个字段（颜色在预制体里，两处都能定色会让人分不清哪处生效）。

### R8 不做 `EnemyCombatState`

- **设计案**（阶段 2 §2.3）：把敌人的受伤状态（HP、`_lastBallId`、`TakeDamage` 判定）提到 Logic 层的新类型。
- **实际**：HP 留在 `EnemyActor`（`Mathf.Max(0, hp - RoundToInt(amount))`）。`_lastBallId` 去重锁**随球 ID 一起消失**了（球不再直接伤害敌人，格子系统按归属表结算，一个目标在一格里只出现一次）。
- **为什么**：去掉去重锁之后，"敌人受伤"只剩一条减法，没有独立规则可测。**触发条件**：出现抗性 / 护甲 / 多段血条 / 受击免疫时再抽。

### R9 "只有状态转换才产生伤害"改为"每次落地都结算一次冲击"

- **设计案**（阶段 1 §A12 / 阶段 3 §1.2）：状态转换时产生一次基础伤害（全局设定）。
- **实际**：`GridLogic.OnBallHit` = **切换状态（可能没切）＋ 每次都给一次该状态的冲击**（伤害 / 击退取自 `tile_state` 行）；`SwitchState` 与"给冲击"是两个独立入参，三种组合（球的落地 / 状态自发起转换 / 开局加载）各用一种。
- **为什么**：照抄设计案会**静默改掉白模的伤害节奏** —— 白模是"每一颗水球落地都对这一格敌人造成一次伤害"，与那一格是不是已经是泥浆无关。只挂在"转换"上会让重复砸同一格的第 2、3 颗球全部失效（要等 8 秒泥浆到期才能再打）。现在的写法与白模逐条一致：**伤害照给、泥浆计时不重置**（同状态不重入 ⇒ 不刷新）。回归测试：`G5_同一格重复落球伤害照给但计时不重置`。

### R10 数值分界按"紧耦合同源"重排

- **设计案**（阶段 1 §4.4 样例表）：例如"投掷最大距离 → SO""攻击间隔（玩家）→ SO""敌人击退力度 → SO"，而"敌人移动速度 / 耐久 → Luban"。
- **实际**：把**同一次投掷**的四个参数（时长 / 弧高 / 最远 / 最近）放进同一张 `projectile` 行；把**同一次受击**的三个参数（接触伤害 / 击退冲量 / 速度上限）＋ 无敌时长 / 重试延时 / 攻击间隔放进同一张 `player` 行；把"状态转换的伤害与击退"放进 `tile_state` 行；只有**观感与冲量**（球/阴影/瞄准环半径、压扁比例、冲量强度、质量下限、查询余量、相机平面深度）留在 `ThrowTuning` SO。
- **为什么**：§4.4 自己的第 2 条规则是"紧密耦合的数值必须同源"，而它的样例表把"球的射程"与"球的时长"拆到了两个来源。两个来源的同一个概念一定会在某次调参后分家（"球飞 5 米但要飞 3 秒"），而那种缺陷不报错。

### R11 战斗输入直读 `Mouse.current`

- **设计案**（阶段 1 §3.8 / 阶段 2 §2.11）：走 `InputProvider` / `InputBuffer`，不直读 `Mouse.current`。
- **实际**：由 `InputProvider`（**仍然是唯一采样点**）在 `Update` 里直读 `Mouse.current`，产出 `AimScreen` / `AttackPressedThisFrame` / `AltAttackPressedThisFrame` 三个**渲染帧**字段；`ThrowController` 只读这三个字段。
- **为什么**：`InputSys.inputactions` 的 Player map 里**没有**攻击与瞄准动作（只有 Move / Interaction / Pause / Jump / Dash / Grab），而动作表是三层共用资产，改它要重新生成 95 KB 的 `Generated/Input/InputSys.cs`（生成物 diff 淹没真实改动）并牵动 UI 侧 EventSystem 接线。契约"唯一采样点"仍然成立，缺的是"可重绑 / 手柄支持"。**迁移三步**已写在 `InputProvider.SamplePointer` 注释里：① 往 Player map 加 `Attack` / `AltAttack`（Button，绑 `<Mouse>/leftButton` / `rightButton`）与 `Aim`（Value/Vector2，绑 `<Mouse>/position`）；② 重新生成 `InputSys`；③ 把 `SamplePointer` 里的三行换成读动作。**触发条件**：出现键位重绑或手柄投掷需求。

### R12 HUD 面板放在 `E_UILayer.Bottom`

- **设计案**（阶段 2 第八批）：HUD 走 `UIMgr`，未指定层。
- **实际**：`HudPanel.Layer => E_UILayer.Bottom`、`CanBeHideByKey => false`。
- **为什么**：不是为了好看，是为了不挡 Esc。`UIMgr.TryCloseTopmostPanel` 按 `System → Top → Middle → Bottom` 找第一个活着（且未隐藏）的面板，遇到 `CanBeHideByKey == false` 的会**就此停下、不再往下层找**。HUD 放 Bottom 且不可关闭 ⇒ 它永远排在暂停面板之后被检查，暂停键行为不受影响。

### R13 白模**本轮不删**

- **设计案**（阶段 1 §D5 / 阶段 2 §3.3）：迁移后 `Prototype/` 与 `Prototype2/` 整体删除。
- **实际**：迁移代码落地时两个白模目录**原样保留**，删除作为独立一步（见 §5 遗留项）在验收通过后执行。
- **为什么**：验收要用的是"新切片能跑"，而删白模会让旧场景立刻变成一片 missing script —— 那会把"验收失败"与"删早了"两件事混在一起，无法区分。隔离成本是 3 行 `using` 别名（白模测试与新逻辑层有 `Steering` / `EnemyLogic` / `EnemyVisual` 三个同名类型）。**注意**：别名与白模同生共死，删白模时一并删。

### 4.3 进 Play 前先点 `StartBtn`

`GameRoot.Awake` → `GameManager.ChangeState(Menu)` → 发 `RequestPause` ⇒ **菜单状态下 `timeScale = 0`，整套战斗是冻结的**。点 `BeginPanel` 的 `StartBtn`（物体名必须叫 `StartBtn`，`BasePanel` 按名字接线）才进 `Running`，同时显示 HUD。

Esc 的既有交互（不是本次引入）：`Running` 按 Esc → 暂停并弹暂停面板；再按 Esc → **只关掉暂停面板**（状态仍是 `Paused`）；第三次 Esc → 回 `Running`。原因：`TryCloseTopmostPanel` 命中就 `return`，不继续做状态切换。
