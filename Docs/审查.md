## 2026-10-05 · 决定：GameRoot 收口（唯一真单例 · 伪单例由它持有）

**目标**：`GameRoot` 负责管理与驱动每个场景的东西，使三件事各自只有唯一答案——**谁造、谁清、别人怎么拿到它**。

**决定**

1. `GameRoot` 升为**唯一真单例**（`Singleton<GameRoot>`）。
2. 五个伪单例改成**普通类（可实例化，不是静态类）**：`ConfigModule` / `AssetModule` / `UIMgr` / `GameManager` / `AudioManager`。由 `GameRoot.Init` 统一 `new`，`OnDestroy` 逆序 `Dispose`；它们的"单例属性"来自"GameRoot 只 new 一份"，生命周期由 GameRoot 持有。
3. 取用路径统一为 `GameRoot.Instance.*`，全工程不再有第二个 `Instance` 出口。
4. 删除 `BaseManager<T>` 与 `MonoMgr`（协程宿主由 GameRoot 承接）；`Singleton<T>` 只留给 GameRoot。
5. `InputProvider` 归口到 GameRoot 驱动（自驱 `Update` 取消），驱动入口表述随之更新。

**为什么是普通类而不是静态类**：① C# 静态类**不能实现接口**，`IUIOperation` / `IService` 的注入会卡住；② 静态字段有跨测试、跨 Play（Domain Reload 关闭时）残留问题。

**三件套规范（每个伪单例，实例方法）**

```
IsReady { get; }   只读状态；别处禁止用 null 判断代替它
Init(...)          唯一构造点；内部顺序：先建依赖，最后 IsReady = true（不留半个就绪）
Reset()            清空自身状态并 IsReady = false；可重复调用；不释放 Unity 资源
Dispose()          归还资源 / 退订 / 清引用 → 以 Reset() 收尾；必须幂等
纪律：只有 GameRoot 调这三个；"重复 Init 抛异常"是这条纪律的检测器
```

**对象四分类与收口方式**

| 类别 | 例子 | 收口方式 |
| :-- | :-- | :-- |
| 进程级服务（伪单例） | `ConfigModule` / `AssetModule` / `UIMgr` / `GameManager` / `AudioManager` | 普通类，`GameRoot.Init` 里 `new` 并持有 |
| 唯一真单例 | `GameRoot` | 它自己 |
| 场景级组合根 | `CombatRoot` | 留在场景里，`Awake` 时注册给 GameRoot；由 GameRoot 驱动 `Tick` / `FixedTick` |
| 场景级零散对象 | `Fountain`、敌人、球、瞄准件 | 装配期**集中收集一次**（注册或集中遍历），不再手拖数组、不再各自 `Find` |

**问题定性（此前讨论的结论）**

- **不是问题**（之前被放大）：面板"无法构造注入"（面板取 `GameRoot.Instance.*` 即可，入口唯一就够）；`combat` 的场景引用（场景对象注册给上层本来就是正解）；`fountains` 手拖（那是收集方式问题，与收口无关）。
- **是真约束但照做即可**：唯一构造点、逆序清理、跨层接口（`IUIOperation` / `IService`）仍由 GameRoot 造实例后注入。
- **真病根：现有实现早已越过框架契约**
  1. `BaseManager<T>.Instance`（`Foundation/BaseManager.cs:27-55`）任何位置、任何时刻都能反射构造管理器 → **装配权被下放**；找不到私有无参构造时只 `LogError`，`instance` 永久为 null（缺陷 D20）。
  2. `Singleton<T>.Instance`（`Foundation/Singleton.cs:15-31`）还会自己 `new GameObject` ＋ `DontDestroyOnLoad` —— 连"谁造、造在哪个物体上"都不在场。
  3. 逻辑层 `UIInputLogic` 直读 `GameManager.Instance` —— 契约 #1 的例外只给了组合根与驱动点。
  4. `UIMgr` 借 `MonoMgr.StartCoroutine` 轮询面板加载 —— 契约 #2 之外的**第五个驱动源**（协程每帧被 Unity 推进）。
  5. 生命周期无唯一归属的症状：`SaveService` 空实现仍每帧 Tick（D8）、`PauseService.Reset()` 零调用（D10）。
  6. 命名空间与目录不一致：`GameManager` 文件在 `Presentation/Root/` 却住 `Logic` 命名空间；`Logic` 文件里出现 `Presentation` using。

**收口清单（真正要改的只有 5 条）**：① GameRoot 成为唯一真单例；② 五个伪单例改普通类、GameRoot 里 `new`／逆序 `Dispose`；③ 面板与逻辑层取用路径统一为 `GameRoot.Instance.*`；④ `UIMgr` 轮询协程改由 GameRoot 每帧推进（删 `MonoMgr`）；⑤ `InputProvider` 归口，驱动入口表述与 N2 一并裁决。

**验收判据**：任意时刻问"这东西谁造的、谁清的、别人怎么拿到"只有一个答案；日志或测试里能看到数量与顺序（如"喷泉 3 个 / 格子 400 个"、构造顺序断言）；全仓只剩 `GameRoot` 一处 `Instance`。

**迁移批次**：批 0 口径 → 批 1 三个已有 static 模块补 `Reset()` ＋ 两条测试 → 批 2 GameRoot 收口并删 `MonoMgr` → 批 3 `GameManager` → 批 4 `UIMgr` → 批 5 `AudioManager` → 批 6 `InputProvider` 归口与文档同步。

**推论 / 待定（必须在批 2 之前定）**："普通类实例由 GameRoot `new` 并持有"这条模型会自然推出 **GameRoot 必须常驻**（`DontDestroyOnLoad`）：若 GameRoot 每场景重建，新 GameRoot 会重新 `new` 一份 `UIMgr` / `AssetModule`，缓存、UI 三件套、`GameState` 全部重来。而现在的 `_dataLayerOwner` 幂等守卫 + Data 层 static 是为"GameRoot 不常驻"设计的，两者要对齐：**要么 GameRoot 常驻（场景对象改为注册制），要么持有者与 GameRoot 分离**。

## 2026-10-05 · 待改：进入冲击只随「真的发生了状态转换」结算

**现状**（`GridLogic.cs:205-213`，照白模逐条对齐写的）：

```csharp
public bool OnBallHit(Vector3Int cell, in BallSpec ball)
{
    if (!_cells.Contains(cell)) return false;
    SwitchState(cell, ball.TileState, applyEnterImpact: false);  // 切换可能失败（该格已经是这个状态）
    ApplyEnterImpact(cell, ball.TileState);                      // 但冲击每次都结算
    return true;
}
```

注释写明的口径是"**伤害照给，计时不重置**"（因为同状态不重入，泥浆计时不刷新）。

**要改成**：只有 `SwitchState` **成功**（状态真的变了）才结算进入冲击；状态没变就不给"转换"带来的伤害。
落法：`OnBallHit` 收成一句 `return SwitchState(cell, ball.TileState, applyEnterImpact: true);`，删掉无条件调用。

**连带影响（改的时候一并处理）**

1. `GridLogic.cs:199-204` 那段"为什么已经是该状态也要结算一次冲击"的注释要重写——它论证的正是被推翻的行为。
2. `战斗框架Tests.cs` 共 8 处 `grid.OnBallHit(...)`（`:350 / 371 / 390 / 410 / 418 / 439 / 465 / 485`）；凡断言"同一格二次投球仍造成伤害"的用例都要改，需逐条核对，不能整批替换。
3. 不受影响：同状态不重入（泥浆计时仍不刷新）；表现层的落地冲量与特效仍照旧发生（`LandingResolver` 的物理冲量是另一条路）——即"同格连续投球"之后逻辑层不再产生伤害，但视觉与物理照动。
4. 边界待定：`TileStateMachine.SwitchTo` 对**未注册的 id** 也返回 `true`（`_current` 变 null）。按"发生了转换"口径，这种情形仍会产生一次冲击；若不希望如此，要另加判定并一起改。

## 2026-10-05 · 决定：玩家侧收口（PlayerStats 归属 · 玩家分层状态机 · CombatRoot 退回世界侧）

**命名**：`PlayerResources` → **`PlayerStats`**（内容 = 水球计数 ＋ 血量）。

**现状问题（已核）**：玩家的装配分散在三处 —— `PlayerController.cs:211` 造 `PlayerLogic`、`PlayerHealthController.cs:59` 造 `PlayerHealth`、`CombatRoot.cs:167` 造 `PlayerResources` 与 `ThrowController`；而 `PlayerLogic`（135 行）实际只覆盖"移动 ＋ 冲刺资格"（持 `PlayerConfig` / `InputBuffer` / `MoveGroup`），名不副实。

**归属与边界（已定）**

- `PlayerStats`（水球 ＋ 血量）由 `PlayerLogic` 内部组合持有。
- `CombatRoot` 退回**世界侧**：格子 / 敌人 / 波次 / 落地。
- 投掷归**玩家侧**（待细化的点：资格与资源消耗在玩家侧，而"生成球对象、走物理、触发落地"仍在表现层 —— 见本节末的讨论）。

**玩家分层状态机（方向已定，细节待议）**

- 采用**领域式分层**：移动 / 战斗 / 状态效果（buff）**各一台**，取代现在"只有移动一台"。
- 依据：Dasuus 的设计案里 HFSM 三层仍标"待细化"、M1 明确不建 `HFSMController` / `ModifierLayer`；其 `参考代码索引.md:52` 还提醒参考代码中是单层状态机（`ActorStateMachineWithTimer` 与 Buff 修饰层只是"形似"）⇒ **本项属自研，没有现成实现可抄**。
- 沿用的既有硬规则：`ActorLogic` 不做状态转移决策、不认识具体状态类；**状态机由状态组按需持有**（Dasuus D15 / D20，本项目 `MoveGroup` 已是这个形态）。
- 待议：① 层间仲裁方式（串行门禁 vs 并行合并）；② 每层的状态集与各自仲裁者；③ 层与 `ActorLogic` 速度账本（唯一写者）的关系；④ 改动顺序（建议先收口装配权，再动结构）。

**额外议题：移动手感（加惯性）**

- 目标：参考 Dasuus 给玩家移动加惯性 / 转向衰减，改善现在"当帧即停"的平庸手感。
- 已核实现状：底层协议两边一致（`ActorLogic` 帧首读引擎真值 → 帧内只累加提交 → 帧末一次写出；**玩家速度只有一个写者**），带惯性的能力也已经在本项目基类里（`ApproachX` / `ApplyExtraForce` / `extraForceScale`）；差别在**玩家侧没启用**：`MoveState` 是"当帧整体接管为 方向 × `moveSpeed`"，`IdleState` 当帧 `StopMove()`，`PlayerConfig` 的 `moveAcceleration` 与 `turnDecayRate` 对玩家是死字段（敌人侧另由 `EnemyCharacterFactory` 折算）。
- 因此"加惯性"不是从零实现，而是把已有字段接上；要一并回答：停手后多久归零、与格子减速（`SlowMultiplier`）如何叠加、与击退 / 撞墙的交互，以及"零惯性"假设被打破后 `StopMove` 的语义。

### 边界补充（同日修订，玩家 ↔ 世界）

- `CombatRoot` **持有玩家引用**；**玩家是否掉血、掉多少由世界侧通知 / 调用触发**（与"世界通知某个怪物扣血"走同一条路），而不是玩家自己去找敌人查。
- 玩家**不判断投掷落点格是否合法**（那是世界信息）；投掷或其它"影响世界"的行为只表达一个**意图**（`Request` 通知或等价方式），**是否被采纳由世界侧自行判断**。
- 职责切分因此明确为：**玩家侧** = 自身资格（弹药 / 冷却 / 射程）＋ 受影响后的表现；**世界侧** = 落点合法性、改哪一格、伤害多少、以及"谁被打到了"。
- 待细化：投掷"意图"的载体（事件 `RequestThrow` vs 直接调用世界侧接口）、以及世界侧"通知扣血"的具体路径（现有实现是 `PlayerHealthController` 调 `PlayerHealth.ApplyDamage(amount, now)`）。

### 设计引用：移动惯性（执行期比对代码）

- 参考：`T:\GAMES\Dasuus\Docs\速度设计.md`，其中三条与本项直接相关：① **Δa 单真源**（加速度只在一处算）；② `v^intent` / `v^external` 这类"算完就没用的中间量"**不跨帧持有**（"一个算完就没用的数，只要活得比一帧久，就会开始生产 bug"）；③ **"状态转移规则本身就是数值设计的一部分"**（改状态机与改参数常常是同一件事）。
- 本项目待接上的既有件：`CharacterConfig.moveAcceleration` / `turnDecayRate`（`PlayerConfig` 继承自它，玩家侧目前无消费者）、`ActorLogic.ApproachX` / `ApplyExtraForce` / `ClampSpeed` / `SpeedTargets`、`extraForceScale`（玩家填 0 = 不施外力）。
- 执行期需要比对代码后再定的四件事：停手后多久归零、与 `SlowMultiplier` 的叠加顺序、与击退 / 撞墙的交互、"零惯性"假设被打破后 `StopMove` 的语义。

### 决定：层间仲裁先采用「串行门禁」（方案 A）

- 顺序即语义：**状态效果层 → 战斗层 → 移动层**。每层只向下层输出"门禁 / 锁"（`SpeedScale`、`AllowMove`、`AllowCombat`、`MoveLocked`），由移动层做最终决策。
- **只有移动层拥有"写速度"的权限**；另两层只能提交门禁与锁 —— 与既有不变量"玩家速度只有一个写者"一致。
- 路线：**先 A 后 B**。A 需要的接口（门禁 / 锁 / 提交结构）B 全都要用，不白写；方案 B（并行提交 + 单一合并）留到"多来源同时修改同一量"成为常态时再上，且**合并结果当帧用掉、不留字段**（对应 Dasuus"中间量不跨帧持有"）。
- 待定细节：① `SpeedScale` 是乘数还是"目标上限"；② "锁"的语义（硬直 = 速度归零，还是衰减到 0）；③ 输入屏蔽与 `InputBuffer` 窗口的交互（被屏蔽期间按下的冲刺，解锁后该不该还算数）。

## 2026-10-05 · 待改：`AttackCooldown` 并入战斗层（CombatGroup）

**现状**：`Logic/Player/AttackCooldown.cs`（39 行）是一个独立的冷确类，只做一件事 —— 存"下次允许攻击的绝对时刻"，回答 `CanAttack(now)`；迁移自白模 `ThrowSpawner._nextAttackTime` 那个裸 `float`。它现在与战斗层没有任何结构关系，只是被 `ThrowController` 调用。

**决定**：并入玩家**战斗层**（CombatGroup）的逻辑，不再单独存在。

**判定依据（决定并入方式的关键问题）**：**冷却期间玩家能不能行动？**

- 若冷却期**有行为**（后摇动画、不能转向、不能投但能走）→ 那段时间就是一个**状态**（如战斗层的 `ThrowRecoveryState`，时长用 `TimedStateBase` 表达，"冷却"= 该状态未结束）。同理与既有先例对齐：`DashState` 的手感就是"时长由状态表达"（Dasuus D9：退出条件全部交回 `IsDone`，由时长表达）。
- 若冷却期**没有行为**（纯粹"这段时间按了不给投"，人可以照常移动/瞄准）→ 它只是**资格计时器**，不该做成状态；收进 `CombatGroup` 内部作为一个字段（保留"绝对时刻"的写法，不用"剩余秒数"，因为前者不受暂停影响、也不需要每帧累减）。

**连带口径（别只改一处）**：`PlayerLogic` 里 `_lastDashAt + dashCooldown`（`CanDashNow`）是**同一类东西**——移动层的冷却，目前是裸字段。要么两处都保留为"资格计时器"，要么两处都状态化，避免移动层与战斗层出现两种口径。

**删除时机**：随"玩家侧收口"一起做（`PlayerStats` 归属 `PlayerLogic` 那一批），不要单独先动。

### 决定：冷却统一为一个通用件（投掷冷却 / 冲刺冷却共用）

`AttackCooldown` 与冲刺冷却要**复用同一套设计**——上层加一个通用类，两处只是名字不同。

**现状（冲刺冷却目前是散落字段）**，都在 `Logic/Player/PlayerLogic.cs`：

```
:26   private float _lastDashAt = float.NegativeInfinity;
:97   CanDash(now)        → CanDashNow(now) && _buffer.CanConsume(InputType.Dash, now, dashBufferTime)
:103  TryConsumeDash(now) → CanDashNow(now) 判定后 _lastDashAt = now
:130  CanDashNow(now)     → now - _lastDashAt >= _player.dashCooldown
```

**通用件形状**（与 `AttackCooldown` 现有 API 对齐，等于把它改名复用）：

```csharp
public struct Cooldown   // 或 class；纯逻辑、只回答"现在能不能用"
{
    private float _nextAllowedTime;                 // 绝对时刻，初始 = 负无穷（开局即可用）
    public bool  CanUse(float now);
    public void  MarkUsed(float now, float interval);   // interval ≤ 0 → 无冷却
    public void  Reset();
    // RemainingSeconds(now) 目前无消费者，需要时再加，不预先塞
}
```

**要点**

- 两处实例分别归**战斗层**与**移动层**持有（不是全局件），仍是"资格计时器"而非状态 —— 与上一节的判据一致（冷却期无行为就不做成状态）。

**落地要点**

1. **逻辑层零引擎类型** ⇒ 状态不能自己 `AddComponent<BoxCollider2D>`。改由状态通过 `TileContext` 的**表现端口**声明意图（"这一格加占位物：树（含碰撞箱）"），由表现层持有资产 / 碰撞体模板并执行。备选：直接走已有的 `TileStateChanged`，由表现层按状态 ID 决定建什么。

5. 与"双层状态（地面 / 占位）"配合更顺：地面层状态只管"贴地效果 ＋ 对目标的修饰"，占位层状态只管"占位物（贴图 ＋ 碰撞箱）"，两层各自 `Enter` / `Exit`，**不需要任何通用字段**。

### 同日评审：命名统一（Director / Manager 两层）＋ 当前方案的不妥之处

**（一）`PickupManager` 到底是 Manager 还是工厂？**

它的实际职责是 **造（实例化 + 注入依赖）＋ 持（列表与生命周期）＋ 驱（每帧 Tick）**。三件事合起来就是"让一类实体按规则运转"，不是单一工厂。

**建议的命名规范（两层后缀，互不重叠）**

| 层级 | 后缀 | 成员 | 判据 |
| :-- | :-- | :-- | :-- |
| 进程级件 | `XxxModule` / `XxxManager` | `ConfigModule`、`AssetModule`、`UIMgr`、`AudioManager`、`GameManager` | 跨场景、由 `GameRoot` 持有、有三件套 `Init / Reset / Dispose` |

**（二）当前方案的六处不妥（按严重度）**

1. **`CombatRoot` 正在往上帝类长**：装配 ＋ 收集场景物件 ＋ 提供世界信息 ＋ 驱动 4~6 个执行器 ＋ 裁决投掷 ＋ 订阅事件 ＋ 清理。建议把"裁决"外置成小的世界规则件（如 `ThrowArbiter`），`CombatRoot` 只装配与转发。

3. **`LandingResolver` 归属未定**：它现在由 `CombatRoot` 直接驱动，自己实现 `IBallLogicEffectContext`；而落地是球生命周期的一环 ⇒ 应由 `BallDirector` 驱动，否则"球的落地"有三个管理者（`BallDirector` / `LandingResolver` / `CombatRoot`）。

5. **清场入口缺失**：打空重来只清了敌人（`PlayerHealthController:151` → `WaveDirector.ClearAll`），球与落地队列各自在别的链上清（`ThrowController:82/180`、`LandingResolver:94`）。三个 Director 之后需要统一入口：`CombatRoot.ClearAll()` → 各 Director 清各自的。
6. **两条运动件状态机的重复**：球（飞行 / 落地 / 结算）与掉落物（抛物线 / 待拾取 / 追踪 / 已领取）机制相同、基类分开。先各自实现，等第三处出现再考虑抽通用骨架。

| 事 | 归谁 | 说明 |

| 高亮的**表现**（色块 / 描边 / 图） | **特效系统**（`EffectModule` ＋ 一个新的 `EffectId`，与 `LandingRing` 同路） | 资产与画法由特效驱动自持；`TileAimView` 这个 MonoBehaviour 随之退场（白模件） |
| **瞄准目标解析**（瞄准点 → 射程夹取 → 吸附到格） | **逻辑层共享纯函数**（建议 `Logic/Grid/AimResolver`） | 吃 `GridGeometry` ＋ 瞄准点 ＋ 射程 → 输出 `cell / worldCenter / inReach`。**球的落地吸附必须与它同一份**，否则"看着能扔到、其实扔不到"会以另一种形式回来 |
| **合法性**（这格能不能投） | 世界侧（`GridLogic.HasCell`，将来含占位 / 阻挡） | 按已定的玩家 ↔ 世界边界 |
| **播放与显隐** | 表现层（每渲染帧：取意图 → 问合法性 → 调特效系统） | 渲染帧相位，符合帧相位口径 |

**待确认（讲特效系统那一簇时核）**：`EffectModule` / `EffectHandle` 是否支持**持续型、每帧更新位置、可停止**的效果。支持 ⇒ 高亮就是一个持续特效；不支持 ⇒ 要么给特效系统补"持续效果"能力，要么高亮保留为常驻件（但资产仍由实体自持）。

### 同日决定：瞄准归玩家逻辑（＝投掷的一部分）；高亮经端口调 `EffectModule`

**归属**：`ThrowController` 拆掉之后，"瞄准"**不是独立系统**，它就是**投掷**的一部分 ⇒ 归**玩家逻辑**。瞄准的结果（`AimResult { cell, inReach, hasAmmo }`）同时喂给"开火判定"与"格子高亮"。

**依赖约束（必须指出）**：`PlayerLogic` 在 **Logic 层**，而 `EffectModule` 在 **Presentation 层** —— 逻辑层零引擎类型、不引用表现层，所以**不能直接 `EffectModule.Play(...)`**。两种落地：

| 方案 | 形状 | 评价 |
| :-- | :-- | :-- |
| **端口（推荐）** | 玩家逻辑持有一个注入的窄接口，如 `ITileHighlight`（一个方法：高亮某格 / 隐藏），**表现层实现它、内部转 `EffectModule`**；装配期由组合根注入 | 语义上"玩家逻辑使用 EffectModule"成立，依赖方向仍是 Logic → 抽象 |
| 事件 | `TileHighlightRequested` 发出去，表现层订阅后调 `EffectModule` | 不推荐：高亮是**每帧的调用语义**，事件是广播语义 |

**帧相位**：按同日定的口径（物理帧只放"角色移动 ＋ 参与物理的逻辑"），**瞄准属非物理逻辑 ⇒ 渲染帧**。所以它不进 `FixedTick` 流程，而由驱动方每渲染帧调（形如 `logic.UpdateAim(mouseWorld)`）；"屏幕 → 世界"这一步由表现层提供（只有它认识相机）。

**`ThrowController` 消失后的分发表（汇总）**

| 原本在它里面的 | 新归属 |
| :-- | :-- |
| 鼠标屏幕坐标 → 世界坐标 | 表现层（相机所在处） |
| 瞄准（吸附到格、射程） | **玩家逻辑**（战斗层的投掷，渲染帧） |
| 弹药 / 冷却资格 | 玩家侧（`PlayerStats` ＋ 统一冷却件） |
| 落点合法性、是否采纳 | `CombatRoot` ／ 世界侧 |
| 生成球、驱动飞行、落地 | `BallDirector`（原临时名 `BallManager`） |
| 瞄准格高亮 | 逻辑层发**事实事件**，表现层订阅后经 `EffectModule` 更新（见本节末的裁定） |

### 同日修订：不走端口，改由 `EffectModule` 逻辑下沉

**口径（用户）**：不使用"逻辑层持有端口、表现层实现"的写法；改成 **`EffectModule` 下沉**——它给逻辑层提供 `.Play` 这类方法，内部再对表现层的实体进行操作。收益：**以后表现层依赖变化时，只改 `EffectModule` 内部的转发，调用点不动**。

**这条决定要一并处理的四件事**

1. **`EffectModule` 的位置与归属**：它现在在 `Presentation/Effects/` 且是**静态类**。逻辑层要能用它，"下沉"必须落到实处——是搬到 `Foundation/`，还是做成"语义化的表现请求中心"（位置可留表现层、但明确它是跨层唯一的出口）。
2. **它与"消灭全局静态入口"的关系**：`GameRoot` 收口的方向是"任何地方都能拿到的全局入口要清掉"，而 `EffectModule.Play(...)` 恰恰是一个静态全局入口。所以必须同时定：**谁初始化它、谁清它（三件套）、未初始化时 `Play` 必须静默忽略**（EditMode 里跑逻辑层时不会炸）。
3. **下沉的应当是"语义化方法"，不是底层通用 `Play`**，否则逻辑层要自己构造 `EffectContext`（`Tint` / `Radius` / `Duration`）—— 那等于把表现参数搬进逻辑层。建议形状：
   ```csharp
   EffectModule.HighlightTile(cell, available);   // 逻辑层认识"高亮某一格"
   EffectModule.HideTileHighlight();
   // 内部：翻译成 EffectContext → 交给表现层的驱动 → 想改依赖只改这里
   ```
4. **持续效果的支持**（沿用上一条待确认）：高亮要"跟着格子亮着"，所以 `EffectModule` 要支持**句柄式的持续效果**（创建 / 按帧更新位置 / 停止），否则每帧 `Play` 会变成每帧新建特效。

### 同日修订：驳回「`EffectModule` 逻辑下沉」，先捋全局

上一条（`EffectModule` 下沉、逻辑层直接调 `.Play`）**先驳回，回到待议** —— 它对"逻辑层该认识表现参数到什么程度"这件事没有把握之前，不适合定。

**全局：现在的跨层通信一共有四种机制**

| # | 机制 | 现有代表 | 适用判据 |
| --: | :-- | :-- | :-- |
| 1 | **事件总线**（`EventBus<T>`） | `TileStateChanged`、`PlayerHealthChanged`、`WaveChanged`、`RequestPause`、`RequestHudRefresh` | "通知某事发生"：过去式、不需要返回值、听众可能不止一个 |
| 2 | **回调端口**（接口 ＋ `in` 结构体注入） | `TileContext`（Scheduler/Dealer）、`IBallEffectContext`、`IMovementMotor`、`IGameTime` | "请求某项能力"：祈使式、需要结果或**每帧调用**、听众唯一 |
| 3 | **静态全局入口** | `EffectModule.Play/Initialize`、`EventBus`、`ConfigModule` | 跨场景的纯服务；**这一条正是收口要清理的对象**（谁初始化、谁清、未初始化怎么办都要有答案） |
| 4 | **组合根注入 ＋ 每帧驱动** | `GameRoot` → `CombatRoot` / `PlayerController` → 各执行器 | 装配与驱动权：对象由组合根造、由组合根推 |

**层次与依赖（现状）**

```
Presentation → Logic → Data        （期望方向）
Foundation   被各层共用（无层属性）
Generated    Luban / InputSys，被 Data 与 Presentation 使用
约束强度：靠自觉 —— Scripts/ 下没有 asmdef，编译器不拦（已知痕迹：LogicContext.cs:5、UIInputLogic.cs:1 各有一处 using Presentation）
```

**高亮这件事的三个候选**（用上面的判据回看）

1. **逻辑层直接请求**（端口注入，或下沉静态模块）：符合"每帧调用、听众唯一"的判据，但要么新增端口，要么把静态模块搬到逻辑层可及的位置，动到收口口径。
2. **表现层每帧向逻辑取**（拉模型）：表现层持 `AimResult` 的查询口，每帧问一次再自己播特效。逻辑层不新增任何机制；代价是表现层要认识"瞄准"。
3. **逻辑层发布事实事件 `AimChanged { cell, available }`**（去重后只在变化时发）：表现层订阅后更新高亮。**与 `TileStateChanged` 完全同路**，不新增机制、不动收口口径，HUD/其它表现件将来也能复用这条事实。

倾向：**候选 3**。理由：瞄准结果本身就是逻辑层产出的事实（"我现在瞄着哪一格、这格可不可投"），它不属于"请求能力"，因此不该用端口/静态下沉；去重发布也不会产生每帧垃圾。

### 同日裁定：瞄准以事实事件发布（`AimChanged`）

**决定**：采用候选 3 —— **逻辑层发布事实，表现层订阅后自己决定怎么表现**。用户已确认。

**形状**

```csharp
// Logic/Event/Events.cs（Fact 段）
public readonly struct AimChanged
{
    public readonly bool       HasAim;      // 无瞄准（暂停 / 鼠标压在脚下 / 瞄不到格）时为 false
    public readonly Vector3Int Cell;        // 瞄到的格（HasAim 为 false 时无意义）
    public readonly bool       Available;   // 可投：射程内 ＋ 世界侧接受（落点合法 / 未阻挡）
}

// 发布者：玩家逻辑的投掷（渲染帧；去重后只在变化时发）
// 订阅者：表现层的瞄准高亮件（内部调 EffectModule）—— 表现层内部调用，不跨层
```

**四点口径**

1. **去重发布**：发布者保存上次的 `(HasAim, Cell, Available)`，任一变化才发（与 `WaveDirector.PublishIfChanged` / `PlayerResources` 的既有做法同路）。
2. **`Available` 的合成**：射程（玩家侧）＋ 落点合法性（世界侧，`GridLogic.HasCell` 及将来的阻挡）—— 顺带补上"现在红白两色只表示有没有弹药"那个缺口。
3. **帧相位**：瞄准属非物理逻辑 ⇒ **渲染帧**发布。
4. **它仍属"特效系统"的生产侧**：表现层订阅者通过 `EffectModule` 播 / 更新高亮；`EffectModule` 的"持续效果句柄"能力仍是待确认项（那已是表现层内部的事，不再牵动分层）。

### 同日决定：`GridView` → `TilemapAdapter`

- **角色**：格子的**表现侧**，一半是**数据源**（几何 ＋ 合法格）、一半是**表现**（状态 → 贴图）。`Adapter` 覆盖这两个方向，`GridPresenter` 只覆盖后一半。
- **位置**：`Presentation/Adapters/`（与 `MovementMotor` / `EnemyMotor` 同目录 —— 那里就是"引擎侧实现 / 适配"的家）。
- **影响面（已核）**：`GridView.cs`（类名 ＋ 5 条日志文案）、`CombatRoot.cs`（`[SerializeField]` 字段 ＋ 报错文案）、`ThrowController.cs`（字段 ＋ 构造参数，该类即将退场）、`RenderOrder.cs:25`（注释）；**测试无引用**。
- **更正一条**：MonoBehaviour 改名**不会**丢场景引用（Unity 以脚本资产的 GUID 绑定，只要 `.meta` 随文件一起走），与"抽象化导致 Missing Script"不是一回事。
- **结构拆解**（讲解口径）：① 职责与两个方向 ② 接线自检 ③ 几何折算与自检 ④ 合法格灌入 ⑤ 状态 → 表现（含原贴图记账）。

### 同日裁定：审计九条的回应 ＋ TilemapAdapter 与格表现口径的差距

**逐条回应**

1. **"玩家判合法性"不成立**（用户重申）：玩家只**表达投掷意图请求** → 上层裁决 → 成功了才真正投掷、由各导演执行。因此玩家逻辑不需要向世界"读"合法性，**不需要世界侧查询端口**。副作用：`AimChanged.Available` 只能是**玩家侧口径**（射程内 ＋ 有弹药/冷却就绪），世界侧"接不接受"由裁决回执决定，不进高亮。
2. **"玩家数值两个写者"不成立**：玩家受伤只有一条路 —— 世界（怪物/接触）调玩家侧暴露的**入口** `TakeDamage()`，数据仍由玩家侧自己改；`PlayerHealthController` 要删。口径写成：**世界侧只能通过玩家侧暴露的入口触发（`TakeDamage` / `AddXxx`），不直接改字段。**
3—4. `WaterBallCollected` / `EnemyVisual` 等在讨论中已被判定拆分改造，不作为"违背项"列出。
6. **泥巴减速改"取巧"方案**：让"泥巴减速"debuff **持续时间极短**，格子状态的 `OnTick` **每帧把它重置一次**（对格上的目标）。于是不需要"谁摘"：
   - 离开泥浆 ⇒ 不再续命 ⇒ 自然过期；
   - 暂停 ⇒ 格子不 Tick（`dt = 0`），恢复后立即续上，无感；
   - 实现上**状态只提交**：`OnTick` 里提出"这一格续一次减速"，**效果的执行由外部（执行者）完成**——状态不持有、也不查询"格上的目标"。
   - 注：debuff 的时长语义因此变成"格子续命间隔"，要写在注释里（否则以后调长时长会出现"离开泥浆还慢着"）。
7. **状态机通用逻辑放 `Foundation/`**（与"数学果实集中地基"同一口径）。
   - **技术障碍要一并处理**：现有 `StateBase<TStateTag>` 的构造直接吃 `ActorLogic`（逻辑层的角色账本），搬到地基前必须把宿主改成**泛型或接口**，否则地基会反向依赖逻辑层。
8. **掉落物的"接收权"（上限 / 节流）归 `PickupDirector`**（持有者才知道自己有几种）。
9. **订阅时机两条口径**（解释）：见下方"大白话"段。

**核心问题：`TilemapAdapter` 是否违背既定想法**

方向上是符合的（装配期读 Tilemap，运行期只听事件，逻辑层不认识 Tilemap）。**违背的是"格表现"的模型**，三点：

| # | 违背点 | 现状 | 按你的想法应该是 |
| --: | :-- | :-- | :-- |
| 1 | **只有一层** | 只有"贴地图"（`effectTilemap` 换 `TileBase`） | 贴地图 ＋ **立体图**（树/占位物，锚格脚底、进 Y-Sort 频带） |
| 2 | **状态 → 图写死在代码里** | `TileFor(state)` 的 switch ＋ `mudTile` 单个 Inspector 字段 | 状态定义带**视觉 id / 资产引用**，由资产层解析；**新增状态不改这个文件** |
| 3 | **只有"有没有地板"** | `RegisterCells` 只登记合法格 | 还要有**格属性 / 占位**的来源（可否通行、这格摆了什么） |

另外一条结构上的含糊：它一半是**数据源**（几何 ＋ 合法格）、一半是**表现**（换贴图），现在被当成一个件。按"数据与表现分开"的取向，将来可能拆成"数据源"＋"视觉"两个文件。

### 同日订正：格子状态只提交；`GridView` 的订阅由组合根驱动

1. **格子状态不持有"格上的目标"**：状态只**提交**（如"这一格续一次减速"），**Tick 的效果执行由外部进行**。上一节里"状态要能拿到格上的目标"那句是错的，已作废。
2. **`GridView`（→ `TilemapAdapter`）的订阅方式不合理**：`OnEnable / OnDisable` 自动订阅必须改。
   - 它是**场景里布置的 Mono**（由场景/美术接线，**不由代码创建** —— 不出现"组合根 `AddComponent` 一个 GridView"这种情况）；
   - 但"何时开始听、何时停止听"要**收口到组合根**：改为提供 `Attach()` / `Detach()`（或 `Initialize` / `Dispose`），由组合根在装配期与销毁期显式调用。

## 2026-10-05 · 评审：特效系统（簇 I）—— 基本不动

用户口径：这一簇是自己参与设计的，预期"不需要动"。**逐条核对后同意**，只有一处需要新增能力。

**不该动（设计站得住的五条）**

1. `Play(id, ctx)` ＋ 句柄 ＋ 失败一律返回 `None`（不抛异常）：表现层不得阻塞游戏。
2. 表驱动的扩展点集中在明处（枚举 ＋ `EffectCatalog` ＋ 工厂），且**故意不做 SO** 的理由成立（枚举已承担编译期检查；数量到几十个再谈）。
3. 驱动自治：单例 / 合并 / 池化策略由实现类自己决定，模块不判断。
4. `EffectContext` 的"**读取处归一化**"（属性而非裸字段）：`default` 与部分赋值都不会产生"缩到 1%""透明看不见"这类不报错的坏表现 —— 值得当作全项目的样板。
5. `EffectHandle` 带 `Driver` 引用 ＋ `Generation`(epoch) 防误停新实例；三个驱动的"仪表 / 读数"定位（落地环半径即实际生效范围、碎裂不读随机）。

另外：**它的生命周期本来就是"由 GameRoot 按序驱动"**（Init → Preload → Tick → CleanAll → Dispose，且 `Dispose` 必须在 `AssetModule.Dispose` 之前）—— 它是收口的**正例**，不是待改对象。

**唯一要动的（新增能力，不是改造）**

- **持续效果口**：若瞄准高亮（`AimChanged`）要复用它，需要"更新已有实例"的能力（如 `EffectModule.Update(handle, ctx)`），或约定"变化时 `Stop` 旧的 ＋ `Play` 新的"。二选一。

**要守住的一条口径**

- **只允许表现层组件调 `EffectModule`**，逻辑层不调。有了 `AimChanged` 这条事实链，逻辑层本来也不需要它 ⇒ 与"消灭全局静态入口"的收口口径自然不冲突。

**波及面：集中在"取用路径"与"订阅时机"，而非画法或数据**

结论：**UI 只有"收口"这件事会真的动它；其余设计改动只要事件契约不改名、不改载荷，UI 基本无感。**

**「UI 暂不收口」的代价（不是立刻会崩，但有三条实质问题）**

1. **验收判据失效（最大的一条）**：既定判据是"全仓只剩 `GameRoot` 一处 `Instance`"。UI 保留 `BaseManager<UIMgr>` 单例 ⇒ 判据要改成"除 UI 外全收"，而每开一次例外，判据就再失一点；后来人会分不清"这是有意例外"还是"漏做了"。
2. **驱动入口多一条，帧内顺序不可预测**：`MonoMgr.Update` 让"面板加载完成 → 实例化 → `ShowMe`（订阅 ＋ 可能发 `RequestHudRefresh`）"能在**主循环的任意时刻**发生——包括正在 `CombatRoot.Tick` 的中间。表现是"这一帧的刷新请求被同帧消费还是下一帧"不确定，属偶发问题的温床。
3. **构造权仍然无人负责**：`BaseManager<UIMgr>` 是反射自建（与缺陷 D20 同族：找不到私有无参构造就永久 null、只 LogError），`MonoMgr` 还会自建 `GameObject` ＋ `DontDestroyOnLoad`。UI 若保留例外，就保留了"UI 有时没起来、而没有任何一层负责回答'谁该在什么时候造它'"这个原病。

**建议的最小折中（半收口，成本一处）**：只把**构造权**收回来 —— `UIMgr` 由 `GameRoot` 显式 `new` 并持有，内部职责（面板字典 / 栈 / 协程改轮询）暂不动。这样"谁造 UI"有答案，验收判据可写成"`Instance` 只剩 `GameRoot`；UI 内部取用由 `GameRoot` 暴露"，同时避开了一次性重写 UI 的风险。

### 同日决定：UI 采用「半收口」

**定下的口径**：`UIMgr` 由 `GameRoot` **显式 `new` 并持有**；**面板字典 / 栈 / 协程这套内部职责暂时不动**（没参与设计的那部分不碰）。

**具体动作（4 条，都小）**

1. `UIMgr : BaseManager<UIMgr>` → 普通类：去掉基类与 `Instance`，其余内部逻辑原样保留。
2. **构造函数不做事**：三件套（`ui/UICamera`、`ui/Canvas`、`ui/EventSystem`）的创建从私有构造挪到 `Init()`，并补 `IsReady` —— 与"三件套规范（IsReady / Init / Reset / Dispose）"对齐。否则 `GameRoot new UIMgr()` 的那一刻就发生资源 IO，装配顺序又变得不可控。
3. **取用路径**：`GameRoot` 暴露 `UI` 属性；`UIMgr` 内部的 `Instance.HidePanel<T>()`（`PanelInfo<T>.Hide` 里那一处）改成实例调用；`GameManager` 里那 8 处 `UIMgr.Instance` 随它归 `GameRoot` 持有时一并改为注入引用。
4. **`MonoMgr` 的两种处理（待选）**：
   - **甲**：暂留 `Singleton<MonoMgr>` ⇒ 验收判据要写"`Instance` 只剩 `GameRoot` **与 `MonoMgr`（临时例外）**"；
   - **乙（推荐）**：改成 `GameRoot` 自己 `AddComponent<MonoMgr>()` 持有并注入给 `UIMgr` ⇒ `Singleton<MonoMgr>` 直接消失，判据保持干净"只剩 `GameRoot`"，成本只有两处调用点。注意：面板加载的协程**仍由 `MonoMgr.Update` 推进**（第 2 条代价仍在），只是构造权与取用路径干净了。

**验收判据（更新后）**：全仓 `Instance` 只剩 `GameRoot`（乙方案）/"`GameRoot` ＋ `MonoMgr` 临时例外"（甲方案）；UI 的取用一律走 `GameRoot` 暴露的属性。

**`MonoMgr` 是什么 / 定下乙方案**

它是**协程宿主**（"公共 Mono 模块"）：一个 MonoBehaviour，对外暴露 Update / FixedUpdate / LateUpdate 三个事件，并把 `StartCoroutine` 借给"自己不是 MonoBehaviour 却需要协程"的类。**全项目只有一个用户**：`UIMgr.CoLoadPanel` 用它跑面板加载协程。

它有三个问题：① 是 `Singleton<MonoMgr>`（会自建 `GameObject` ＋ `DontDestroyOnLoad`）；② 是**额外的驱动入口**（三条 Update 事件），与"每帧只有四个驱动入口"的硬契约冲突；③ 它的"通用注册表"设计只有一个用户 ⇒ 抽象不成立。

**决定：乙方案** —— `GameRoot` 自己 `AddComponent<MonoMgr>()` 持有并注入给 `UIMgr`，`Singleton<MonoMgr>` 消失，验收判据保持"`Instance` 只剩 `GameRoot`"。
代价不变：面板加载的协程**仍由 `MonoMgr.Update` 推进**（第 2 条代价还在）。

**后续可选项（丙，将来一步到位）**：直接**删掉 MonoMgr** —— `UIMgr.CoLoadPanel` 本来就是轮询 `handle.IsDone` 的形态，改成"由 `GameRoot` 每帧调一次 `PollLoads()`"即可：
- 需要把协程用栈保存的中间状态改成字段（面板名 ＋ 类型 ＋ `AssetModule` 句柄 ＋ `PanelInfo`）；
- 类型可用 `BasePanel` 基类取组件后转型（`Layer` 等已由基类提供）；
- 收益：驱动入口回到四个，`MonoMgr` 与 `Singleton<MonoMgr>` 一起退场。
（这条不阻塞半收口，作为后续独立小批。）

### 同日修订：`MonoMgr` 暂不动（保持现状）

**决定**：`MonoMgr` 保持 `Singleton<MonoMgr>` 现状，甲、乙、丙三个方案**都缓做**。理由（用户）：只要环境有一定隔离就问题不大 —— 而**它的用户确实都在 UI 层内**（已核：全项目唯一调用点是 `UIMgr.cs:274` 的 `StartCoroutine(CoLoadPanel<T>)`）。

`UIMgr` 自身的**半收口（构造权归 `GameRoot`）保持不变**。

**与既定设计思想的逐条对照**

相合：生命周期由 `GameRoot` 按序驱动（Init → Preload → Tick → CleanAll → Dispose，顺序有明文）＝组合根收口；契约是"逻辑发事实 → 表现组件订阅 → 组件自己决定播"＝逻辑发事实、表现听；形状与颜色在预制体/驱动自己手里＝资产自持；一类特效一个驱动、池化与合并都在驱动内＝不散装；`Tick` 在 `GameRoot.Update`（渲染帧）＝帧相位口径；模块本身没有 MonoBehaviour、不自驱。

**唯一相悖的点**：它是**静态类**（`EffectModule.Play` 谁都能调），"取用路径"没有收口 —— 逻辑层如果愿意，编译也能过。这条**已被收口批次覆盖**（批 1 就是"三个已有 static 模块补 `Reset()` ＋ 由 GameRoot 调其生命周期"），`EffectModule` 恰是那一类件。因此结论是：**不需要为它单独立项**，只要守住"调用方限定在表现层"。

小瑕疵一处：`IEffectDriver.IsSingleton` 在接口上，但 `EffectModule` 并不据此分支（注释写明只用于调试展示与实现自述）—— 接口成员与实际行为不完全对应，属可接受。
