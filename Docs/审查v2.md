## 5 · 设计原则：缺数据要改表，不要加拼装（用户补充，2026-10-07）

> 如果消费方拿不到完整数据，那是**表设计的问题**，不该加一个"拼装方法"去解决 —— 应当着重去设计表。

- 推论一：`SpecCatalog` 那类"把多列拼成一个方便对象"的做法，会掩盖表本身的形状问题（列不够、粒度不对、缺维度）。
- 推论二：`tile_initial` 没有"关卡"维度、`enemy` 没有"掉落"列这类缺口，正确处置是**改表加列**，不是加中间层补齐。
- 推论三：表加列对代码零成本（生成类自动多一个字段，没人读就没影响），所以"表不够用"没有理由靠代码兜。

## 7 · 结算口合并：Slow 不是通用字段（用户裁定，2026-10-07）

**裁定原文口径**：`TileContext` 里**不是每种格子状态都有"减速"**，所以 `ITileSlowApplier Slow` 作为通用字段不该出现在这里；它应当**蕴含在 Dealer 里** —— `Dealer` 不该只是 `DamageDealer`，而是一个**各种效果的结算器**。因此：

1. 接口重新设计（结算口合并/改权）
2. `GridLogic` 里删改字段
3. **逻辑放开给 `TileState`**

**当前状态（被裁定要改的现状）**：

- `TileContext` 三个端口：`ITileScheduler Scheduler` · `IDamageDealer Dealer` · `ITileSlowApplier Slow`
- `GridLogic` 字段：`ITileSlowApplier _slow`（ctor 参数传入，`BuildContext` 里塞给 `TileContext`）
- 实现方：`CombatRoot` 同时实现 `ITileSlowApplier`（含"泥地减速玩家"那条分支）
- 目标侧：`ISlowEffectTarget`（目标自己续减速修饰）
- `MudTileState.SubmitSlow` → `ctx.Slow?.ApplySlow(cell, factor, 0.1f)`

**影响面（执行时要一并改）**：`TileContext.cs`（字段与 ctor）· `ITileDamageDealer/ITileSlowApplier` 两个接口 · `GridLogic`（删 `_slow`、改 ctor、改 `BuildContext`、`Deal` 归入新结算口）· `MudTileState`（提交方式）· `CombatRoot`（实现者改名与实现）· 相关测试（`战斗框架Tests` 的假执行者）

**设计张力（记录在案，供决策时看）**：`TileContext` 的现有注释写着"端口收窄"的理由 —— 状态只该知道"我在哪、现在几点、我能提交什么"，不给门面是为了防止状态顺手改别的格。现在"逻辑放开给 `TileState`"是对这条的放松，两条口径要择一。

**已定（同日）**：① 结算口 = **方案 B**（一个接口、一个入口、效果用结构体描述）；② 放开档位 = **"状态能提交各种效果，但仍不碰目标"**（状态不拿目标列表、不自己施加）。

**目标形态（给执行方的形状）**：

```csharp
public enum TileEffectKind { None = 0, Damage, Slow }

public readonly struct TileEffect           // 效果描述：Kind + 语义化字段 + 静态工厂
{
    public readonly TileEffectKind Kind;
    public readonly float Amount;           // Damage：伤害值
    public readonly float Knockback;        // Damage：击退冲量
    public readonly float SpeedScale;       // Slow：速度乘数（1 = 不减速）
    public readonly float Seconds;          // Slow：这次续命能让修饰再活多久
    public readonly DamageSource Source;    // Damage：来源标记

    public static TileEffect Damage(float amount, float knockback, DamageSource source);
    public static TileEffect Slow(float speedScale, float seconds);
}
// 关键：**只允许用工厂构造** ⇒ Kind 与参数不可能对不上（方案 B"无名槽位 ⇒ 静默错"的风险由工厂堵住）

public interface ITileResolver              // 取代 IDamageDealer + ITileSlowApplier
{
    void Apply(Vector3Int cell, in TileEffect effect);
}

public readonly struct TileContext          // 端口从 3 个减到 2 个
{
    Vector3Int Cell; float Now; float DeltaTime;
    ITileScheduler Scheduler;               // 提交口（Tick / 状态转换）—— 不变
    ITileResolver  Resolver;                // 唯一的效果出口；可为 null（逻辑层单跑测试）
}
```

改动点：

- `TileContext.cs`：删 `Dealer` / `Slow` 两个字段与 `IDamageDealer` / `ITileSlowApplier` 两个接口，换成 `Resolver` 与 `ITileResolver`；保留 `ITileScheduler` 与目标侧的 `ISlowEffectTarget`
- `GridLogic`：删 `_slow` 字段与 ctor 参数；`Deal` 与 `ApplyEnterImpact` 改走 `TileEffect`；`BuildContext` 只塞 `this`（Scheduler）与 Resolver
- `MudTileState.SubmitSlow` → `ctx.Resolver?.Apply(ctx.Cell, TileEffect.Slow(_row.SlowFactor, SlowRefreshSeconds))`
- `CombatRoot`：从"实现 `ITileSlowApplier`"改为"实现 `ITileResolver`"（或改为注入一个结算器）
- 相关测试里的假执行者同步改

**这一档顺手暴露出来的真问题（执行前要拍）**：结算器要能处理 `Slow`，就必须能拿到**格上的全部目标**；而现在的归属表是 `EnemyCellRegistry`（**只登记敌人**），玩家不在里面 —— 这正是当初 `_slow` 由世界侧（`CombatRoot`）注入的原因。两条路：
- (a) **玩家也登记进归属表**（表随之改名，如"格上目标表"）⇒ 结算器完全落在逻辑层，`GridLogic` 自己就能做 `Slow`；
- (b) 保留一个**通用的"目标来源"端口**（比"慢速专用端口"通用），由世界侧提供 ⇒ 结算器仍知道"谁在格上"。

**补充裁定（同日）**：**玩家先作为特殊处理 —— 只能被怪攻击，格子作用不到玩家。**

- 归属表只登记敌人这件事从"缺陷"变成"口径"：结算器就只认归属表里的目标，玩家不登记、格子系统完全不认识玩家
- 于是上面 (a)/(b) 都不用选：`GridLogic` 自己实现 `ITileResolver`，`_slow` 字段与 ctor 参数**彻底删除、不需要任何注入**
- 连带**推翻**此前记录的"有意行为变更 —— 泥地会减速玩家"：`CombatRoot.ApplySlow` 里的玩家分支删除；玩家的伤害来源只剩敌人的接触伤害（`PlayerSpec.ContactDamage`）
- 保留 `ISlowEffectTarget`（由敌人侧实现）；`Deal` 的目标来源也仍是归属表（本来就只登记敌人，行为不变）

**以下两问作废（原样保留便于对照）**：① 新结算口是"一个接口多个方法"（伤害 / 减速 / 将来的效果各一个方法），还是"单个 `Apply(in 效果结构体)` 由结算器分流"？② "逻辑放开给 `TileState`"放开到什么程度 —— 只是"能提交更多种类的效果"，还是状态可以直接做结算（例如拿到目标列表自己施加）？

## 8 · 玩家侧收敛与生命体征统一（用户裁定，2026-10-07）

### ① `PlayerSpec` / `PlayerHealth` / `PlayerStats` 三者归并

**裁定**：三者关系不合理 —— **全部归并成一个 `PlayerStats`**。它只是一个**包装**：包装 `PlayerSpec` ＋ 对外提供数值处理方法；`PlayerHealth` **退役**。包装可以放在 **Data 层**。目的：让外层减少"这个值我要去哪里找"的判断。

**⚠ 与 §4 的冲突（必须对齐）**：§4 的裁定是"**删掉 Spec 中间层，直接吃 Luban 生成类**"，其理由是"Luban 已经生成类/字段就是表列，再抄一份要手工同步"。本节要把中间类恢复。**已定（同日）：读法 A** —— 中间类**不复制表列**，只持有「表行引用 ＋ SO 引用」，对外暴露**合并后的语义访问**。用户口径原话："**绝对拒绝重复抄写表列，这个中间类真的只是一个组合件**"。生成枚举**不包装**（"它已经很易用了"）。

- 读法 A（我倾向）：中间类**不复制表列**，只持有"**表行引用 ＋ SO 引用**"，对外暴露合并后的语义访问。这样 §4 反对的"手抄一份字段"没有被恢复，而"无感取数"成立。

**读法 A 的写法纪律（防止"抄列"从后门回来）**：

- 中间类**只写"被消费的语义点"**（按需暴露），**不逐列转抄整行** —— 没人消费的列不进中间类

- 某语义两端都没有 ⇒ 那是**表缺列**（§5：改表，不要靠中间类补齐）

- 生成代码从此可以真正做到"不出关"：`cfg.demo.*` 只出现在 Data 层的包装实现里
- 已定：生成的**枚举**（`TileStateType` / `BallType`）**不包装**（用户：它已经很易用了）
