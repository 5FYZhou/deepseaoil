# 玩家反馈处理指导思想

> 玩家反馈是真实的体验信号，不是现成的设计命令。  
> 本文用于评论、社区帖子与试玩反馈的整理、过滤和转译。

## 一、核心判断

游戏发布后，它不再只属于开发者。玩家投入了时间、金钱和情感，成为游戏社区的利益相关者；开发者因此需要倾听玩家。但倾听不等于言听计从，专业判断与设计责任仍在开发者手中。

必须区分两件事：

1. **玩家提出的解决方案，通常不是问题的正确定义。**
2. **玩家表达的不满、失望、困惑和沮丧，通常是真实体验。**

声音大不等于问题大，重复多也不等于需求正确。开发者要理解玩家为什么产生这种感受，再判断应当修改机制、改善反馈、调整节奏，还是保持原设计。

## 二、处理原则

- **先记录情绪，再分析原因，最后讨论方案。**
- **保留原始表达，不把玩家的具体建议直接写成需求。**
- **还原发生场景。** 明确玩家在何时、因何动作、被什么结果打断或伤害。
- **寻找未被满足的体验需求。** 例如流畅性、可理解性、公平感、掌控感、成长反馈或情绪回报。
- **用自己的专业知识解决问题，而不是机械满足字面要求。**
- **同时检查设计初衷。** 玩家痛点可能说明设计失效，也可能说明体验引导不足；不能为了消除吐槽而破坏作品核心。
- **允许明确不做。** 与核心体验冲突、证据不足或只代表少数极端意见的诉求，可以记录后过滤。

## 三、从意见到问题的转译

收到反馈时，按以下顺序处理：

1. 截取玩家的原句或准确复述。
2. 标记表层意见、情绪和发生场景。
3. 推断背后未满足的体验需求，并注明这是事实还是解释。
4. 与其他评论比对，识别重复、冲突和相互矛盾的解决方案。
5. 判断根因可能属于缺陷、可用性、节奏、数值、反馈、内容或设计目标不匹配。
6. 提出待验证的问题，而不是立即承诺功能。
7. 汇总后由 CEO 决定是否进入规划。

示例：

- 玩家说“武器耐久度太低”，未必需要无限耐久。真实问题可能是修理流程频繁打断跑图与战斗节奏。
- 玩家说“BOSS 太难”，未必需要整体降难。真实问题可能是攻击模式不公平、反馈不足，或没有提供足够的学习空间。

这两个例子并不意味着上述解释一定成立。它们是待验证的假设，最终仍要依据玩法目标、适用范围和真实体验证据判断。

## 四、整理时的最低输出

每条进入讨论的诉求至少应包含：

| 项目 | 要求 |
| :-- | :-- |
| 原始反馈 | 原句或有出处的准确复述 |
| 情绪信号 | 玩家明确表现出的体验感受 |
| 使用场景 | 问题在何时、何地、如何发生 |
| 表层建议 | 玩家提出的方案，仅作线索 |
| 需求假设 | 对真实痛点的初步解释 |
| 证据状态 | `VERIFIED` / `OBSERVED` / `INFERRED` / `UNKNOWN` |
| 冲突关系 | 与其他意见是否重复、矛盾或覆盖不同人群 |
| 处置建议 | 调查、修复根因、改善引导、延后或不做 |
| 待确认项 | 尚需 CEO 或后续验证回答的问题 |

## 五、不可越过的边界

- 不因为评论数量多就自动增加功能。
- 不把玩家的具体方案当成验收标准。
- 不用“尊重玩家”为理由放弃核心设计目标。
- 不把情绪真实等同于技术判断正确。
- 不在证据不足时承诺实现范围或完成时间。
- 需要修改玩法、数值、资产、接口或验收标准时，仍须进入正式任务规划与 CEO 批准流程。

最终目的不是让所有评论消失，而是理解这些感受为何出现，再用专业能力解决真正的问题，让这款游戏既能回应玩家，也仍然是开发者想做的作品。
